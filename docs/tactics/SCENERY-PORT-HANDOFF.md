# Porting the 3D branch's scenery to the sprite game

Opened 22 September 2026. Nothing in this document is built. Update the status
table when a parcel is claimed, landed or abandoned; a conversation answer is not
evidence that a parcel exists.

The work is cut so that **two agents can pick any two parcels and never edit the
same file**. Each parcel below names the files it owns exclusively. If a parcel
needs to change a file another parcel owns, that is a dependency, and it is
written down as one. The two Stage 0 parcels exist only to create that separation;
without them every parcel here would collide in `environment.js`, `prop-art.js`,
`manifest.json`, `editor.js` and the Pages file list.

6 ground textures:

Three systems come with them, none of which the sprite game has any part of:

- **A day cycle.** `daylight.js` centralises dawn 05:00–06:00, day 06:00–18:00,
  dusk 18:00–20:00, night 20:00–05:00, with a map-fixed east-to-west sun. A map
  may set `time.startMinutes` (0–1439); encounters otherwise open at 08:00.
- **Artificial light.** `light-sources.js` holds `LIGHT_FORMS` (emitter offsets
  per fixture), `LIGHT_RANGE = 30` tiles, and a stepped falloff shared by the
  shader and by detection, `2 ** -max(0, ceil(distance / 5) - 1)`: 100% for the
  first five tiles, then 50%, 25%, 12.5%, 6.25% and 3.125%, zero past 30, with
  each band's outer boundary belonging to the brighter side. A placed prop carries
  `lightMode: 'auto' | 'on' | 'off'`; automatic electric lamps run 18:00–06:00 and
  automatic fires stay lit. Exposure traces from the target's body region through
  the same solids sight already uses.
- **Sweeping spotlights.** A placed prop carries `lightTargets`, one to three
  `{x, y, z}` offsets **relative to the fixture's own tile**, which is what makes
  them survive block capture and undo. One point is stationary; two or three
  interpolate in a loop at one game minute per leg. Unset, a tower aims twenty
  tiles outward and the standalone lamp eight tiles south. The standalone
  `spotlight` uses a 60° cone, the three towers 45°. Any nonzero direct spotlight
  illumination of a visible body region identifies that person immediately, in any
  band, regardless of sneak, stance or foliage.

None of these three fields changes the map schema. `validateMap` rejects unknown
keys nowhere, `parseMap` ends in a `structuredClone`, and `blocks.js` spreads the
whole prop record, so `lightMode`, `lightTargets` and `time.startMinutes` already
survive a round trip through **this** tree today, unread. The one thing the sprite
parser genuinely rejects is a prop `kind` it does not know.

## What "keep the sprite aesthetic" means

The sprite game is not procedural art. Every prop, barrier and ground surface is a
painted **1254 × 1254 PNG** under `dist/assets/environment/`, drawn with a single
`drawImage` from a cropped source rectangle. Porting scenery means producing
paintings and catalog rows, never geometry.

The conventions, with the numbers, are:

- **Projection.** 2:1 isometric. One tile at zoom 1 is **56 × 28 px**. Ground
  axes slope 26.565°, verticals stay vertical, the light comes from the upper
  left. A wall sprite stands 72 px on that 28 px tile; a railing 20 px; jail bars
  62 px; a cut fence 44 px.
- **Files.** RGBA (colour type 6) for props and barriers, RGB (colour type 2) for
  the six ground textures, all 1254 × 1254, all with a generous transparent
  margin and no cast shadow beyond the footprint.
- **Palette.** Olive green, weathered wood, brick rust, warm grey concrete. The
  verbatim clause used on every existing prompt lives in
  `art/environment-prompts.md`; foliage has its own in `art/foliage-prompts.md`.
- **No outline pass.** Separation comes from the painted silhouette itself.
- **Crops.** Alpha ≥ 64 bounding box, generated by `tools/catalog-environment.py`
  into `prop-art.js`. Barrier art also needs a five-number `baseline`.
- **Sizing.** A prop is scaled to fit `visualWidth ?? (w+h)*25` by
  `visualHeight ?? (w+h)*11 + (tall ? 43 : 18)` pixels at zoom 1, anchored at the
  foot of its footprint diamond.

Two gates enforce this and will fail a careless port. `tools/check-assets.mjs`
asserts that the manifest's id list equals exactly the union of `PROPS` keys,
`EDGES[*].art` values and `GROUNDS`, checks every PNG's dimensions and channel
count, and fails on any unreferenced PNG under `dist/assets/environment/`.
`tests/tactics-new-props.test.mjs` then places, rotates, exports and reloads every
id that has both a `PROP_ART` crop and a `PROPS` rule, so a new prop is covered by
the existing suite the moment it is registered.

Three things in the 3D branch's look must **not** come across. Its camera sits at
35.26°, giving roughly 1.73:1 diamonds where this game needs 2:1 at a 45° azimuth,
as `HYBRID-MIGRATION.md` records. Its materials are shaded at runtime; the sprite
paintings carry their own light. And `HYBRID-VISUAL-HANDOFF.md` already rejected
the block-built read of that branch's environment once.

## How the work is divided

Fourteen parcels in four stages.

- **Stage 0** removes the shared-file collisions. It has three parcels and only
  one ordering constraint: **A, then S1**. A writes ten lines into the three
  registries S1 is about to split, so it is cheaper to land it first than to make
  it wait. S2 touches none of their files and can run beside either.
- **Stage 1** is new scenery art. Each parcel owns one asset folder, one catalog
  module, one manifest side-file and one review page, all created empty by S1.
  Any two of them can run at once.
- **Stage 2** is the lighting and ground-cover systems. They own separate new
  modules, but two of them share `light-sources.js`, so those two are ordered.
- **Stage 3** is the one parcel that repaints existing assets, so it holds the
  existing-art lock and runs alone.

### Ownership rule

A parcel may create and edit only the files in its **Owns** row. It may read
anything. If it finds it needs a file another parcel owns, it stops, records the
need in this document under that parcel, and either waits or takes the other
parcel too. Nobody edits a file that is not listed against a parcel; the tree has
files this plan never mentions, and they stay untouched.

New review pages link outward to the existing index only. Do not edit a sibling
page's navigation strip to add a link back: every parcel would edit every page.
Cross-links are the integrator's job at the end.

### Out of scope: character art

This plan is scenery only. A separate line of work owns the roughly 660 character
PNGs and everything that reads them, and no parcel here touches any of it:

- `dist/assets/characters/**`
- `art/*-sources.json`, `art/*-generation.json`
- `dist/tactics/character-art.js`, `red-hats-art.js`, `body-art.js`,
  `body-frames.js`, `flamethrower-art.js`, `flame-nozzles.js`
- `dist/tactics/character-art.html`, `weapon-expansion.html`, `red-hats.html`,
  `bodies.html`

Parcel M holds an existing-art lock, but only over the environment catalog. If a
scenery parcel finds it needs a character file, that is a sign the parcel is
wrongly scoped; stop and say so here.

## Stage 0

### A — Mature trees

**Do this one first, before S1, and land it before S1 begins.** It is the only
parcel that writes into the shared registries on purpose, and it is worth the
exception: it is ten lines, it needs no artwork, and it fixes a live
incompatibility rather than adding a feature. A map authored in the 3D editor with
a mature tree on it is rejected by this tree's parser today with
`Invalid environment props.`, which is the exact failure
`MATURE-TREE-INTEGRATION.md` was written to repair on the other side.

Two kinds, `tree-broadleaf-large` and `tree-pine-large`, both 1×1, solid, tall,
cover 25, visual 180 × 234. The canonical source is `work/mature-tree-core` at
`e529f4b`. It ships **no new artwork**: it aliases the existing tree PNGs and only
enlarges the draw size. The whole upstream change is three files:

1. `environment.js` — the `TREE_VARIANTS` export and one loop that writes
   `PROPS[kind] = {...PROPS[base], visualWidth: 100*scale, visualHeight: 130*scale}`.
2. `prop-art.js` — `"tree-broadleaf-large": {"file": "foliage/tree-broadleaf.png",
   "crop": [93,62,1176,1194]}` and `"tree-pine-large": {"file":
   "foliage/tree-pine.png", "crop": [292,16,1019,1205]}`.
3. `manifest.json` — two `kind: "prop"` entries pointing at the same two PNGs.

All three of those files belong to S1. That is why A goes first and alone: it is
cheaper to write ten lines into the old registries and let S1 carry them into the
new `trees-large` group during its split than to make a compatibility fix wait on
a refactor. If S1 has already started when you read this, do not open those files.
Hand the three-file diff to whoever holds S1 and let them land it inside the seam.

Whether the two variants eventually deserve their own paintings is a separate
question, and a Stage 1 parcel if the answer is yes. There is no resolution
argument either way: the source crop is about 1083 × 1132 px drawn at 180 × 234,
so it is still heavily downsampled. The argument is compositional. In a
fixed-scale isometric view, the same painting at two sizes reads as a distance cue
rather than as two different trees, and this game's camera has no distance. A
broader crown and a heavier trunk would say "older tree" where a scale factor says
"nearer tree".

Watch the footprint either way: the crown overhangs but only the trunk tile is
solid, and the renderer anchors a prop at the foot of its diamond, so a 234 px
canopy covers the tiles behind it. Check it against a standing character.

**Owns.** `dist/tactics/environment.js`, `dist/tactics/prop-art.js`,
`dist/assets/environment/manifest.json`, for the duration of this parcel only.

**Done when.** `npm run check` is green and a map exported from the 3D editor with
both mature trees on it loads here and draws them.

### S2 — Clock, sun and render hooks

**Why.** Every lighting parcel needs to know what time of day it is and needs
somewhere to draw. `app.js` is one dense file; if three parcels edit it the plan
falls apart. One parcel takes it and lands the hooks the others will use.

**Deliverables.**

1. `dist/tactics/daylight.js`, new: the phase schedule (dawn 05:00–06:00, day
   06:00–18:00, dusk 18:00–20:00, night 20:00–05:00) derived from
   `world.clock.minutes`, plus the ambient tint and sun direction for each phase.
   Port the boundaries from the 3D branch's `daylight.js` so the two games agree.
2. `time.startMinutes` on the map schema in `maps.js`, an integer 0–1439,
   validated and preserved through export, import and blocks. Absent means 08:00.
3. The tint itself in `app.js`: a per-frame wash over the finished scene, warm at
   dawn and dusk, cool and dark at night, nothing at midday. It must respect the
   existing layer compositor and must not tint the interface.
4. Three named draw hooks in `app.js`, called with the current camera and tile
   bounds, each defaulting to nothing:
   - a **ground-dressing** hook, drawn after terrain and before props, for K;
   - a **light-pool** hook, drawn after the dressing and before props, for I;
   - an **overlay** hook, drawn after everything, for J's beam.

   this file.
5. A sort convention in `paint-order.js` for a **static burning prop**, which B

   flame clumps as separate objects offset along the depth axis by less than .45,
   never 0, because walls and fences on a tile's sides sort at ±.5 and a unit
   standing on the tile sorts at 0. A campfire that is a prop rather than a burning
   tile has to reach the same result without pretending to be a scorch. Land the
   convention; B fills in the art.
6. The phase on the existing clock readout, and a document,
   `docs/tactics/DAYLIGHT.md`.

### B — Lamps, torches and fires · group `lighting`

Nine kinds, art and placement only. No light is emitted in this parcel; that is I.
Every one of them has to be painted from nothing: the 3D branch builds all thirteen
fixtures as geometry against two shared atlases and ships **no fixture sprite at
all**, so there is no source image to trace. This is the largest painting job in
Stage 1.

`floor-lamp`, `bedside-table-lamp` (cover 25), `gooseneck-sconce` (not solid, wall
mounted), `streetlight`, `streetlight-double` (2×1), `standing-torch`,
`wall-torch` (not solid, wall mounted), `campfire`, `cooking-fire` (2×2).

Two problems to solve rather than inherit. The sprite game has no concept of a
wall-mounted prop: `wall-torch` and `gooseneck-sconce` occupy a tile but do not
block it, and the 3D branch mounts them on the tile's north edge, or east when
rotated. Decide how the sprite renderer offsets them onto the edge, and whether
the editor should refuse to place one away from a wall.

Second, four of the nine burn, and this tree already has a fire idiom worth
copying rather than a second one worth inventing. Three files carry it, and none
of them is the flamethrower's own art:

- **`ground-fire.js`** is the pattern to follow. It is the persistent-burning-thing
  case rather than a one-shot burst: a scorch decal on its own paint layer, plus a
  few flame clumps emitted as **separate depth-sorted objects**, so a unit standing
  in the fire has flames both behind and in front of it and neighbouring walls
  overlap them the way they overlap sprites. `FIRE_FRAMES = 8` at
  `FIRE_LOOP_MS = 800`, hand-drawn fire animated on twos, cached to canvases per
  zoom step. A campfire, a cooking fire and two torches are that shape exactly,
  minus the three-round burn-down.
- **`flame-effect.js`** is the drawing library underneath it: `FLAME_PALETTE`,
  `SMOKE_PALETTE`, `fillFlames`, `smokeCloud`, and the rule in its header that
  keeps fire looking like the painted sprites, which is that **every shape is
  outlined once around its union and shaded in flat bands**, so the outline traces
  only the outside silhouette. It is pure and deterministic in `(options, t)`, so
  a frame can be scrubbed, and a new fire must keep that property.
- **`paint-order.js`** is what makes the split-depth trick legal. Walls and fences
  on a tile's sides sort at ±.5 and a unit standing on it sorts at 0, so a flame
  clump offsets along the depth axis by less than .45 and never by 0. A static
  fire prop that wants a flame in front of the post it sits on needs that
  convention, not a new one.

Honour reduced motion the way `water-preview.js` does.

`flamethrower-art.js` and `flame-nozzles.js` are **not** part of this. The first
draws the weapon on a character and returns early unless the unit is carrying a
flamethrower; the second is a generated table of muzzle positions per character
PNG. Both are character art and both are out of scope.

### C — Guard towers and guardhouses · group `towers`

Three canonical kinds first: `wooden-spotlight-tower` (5×5),
`iron-searchlight-stair-tower` (6×5), `iron-searchlight-ladder-tower` (6×5). The
other fourteen gallery forms listed earlier are a second batch and need the
architect's word.

This parcel has the one genuine rendering problem in the plan. A tower is three
stories tall. The sprite game's tallest prop is a 130 px tree on a 28 px tile, and
a prop is painted at ground level with `paintDepth = x + y`, then dimmed or
brightened by the layer compositor according to the level the player has selected.
A ground-level prop reaching level 2 will be dimmed whenever the player inspects an
upper floor, and will sort against actors standing behind it. Decide the rule
before painting: either the tower is a ground prop with an explicit large
`visualWidth`/`visualHeight` and a documented sorting limitation, or S2's overlay
hook draws it above the compositor. Do not move simulation volumes to make the art
sit right. Stairs and ladders on these models are art; climbing them is not wired
on either branch.

### D — Cargo forms · group `cargo`

Nine new kinds beyond the sprite game's existing `crate-wood`, `crate-steel`,
`crate-stack`, `barrel-single` and `barrels-cluster`: `crate-long`, `crate-tall`,
`crate-strapped` (each 1×2), `crate-pallet` (2×2), `barrel-stack` (1×1),
`barrel-row` (1×2), `barrel-pyramid` (2×1), `barrel-pile` and `barrel-block`
(both 2×2).

The 3D branch offers four finishes per family and five label sets, a 48-way and
then 240-way matrix. Do not port the matrix. A painted sprite is one file per
combination, and 48 files of crate is not a sensible catalog. Pick one finish per
form so the nine read as nine different objects, and treat labels as part of the
painting where they help legibility.

### E — Household furniture · group `furniture`

Six kinds: `dining-table` (1×2), `coffee-table` (1×2), `single-bed` (1×2),
`bedside-table` (1×1), `refrigerator` (1×1), `cabinet` (1×2). Honey timber, aged
cream and sage on the 3D branch; pick one finish each for the same reason as D.

This is the parcel the campaign direction actually needs. `CAMPAIGN-BACKLOG.md`
item 3 asks what a town is and what is on its tile, and item 6 asks what a town's
social services are. Neither can be authored on a map that has only factory
furniture. Say so when handing this over.

### F — Factory machines · group `machines`

Three kinds at 2×3 tiles: a teal metalworking lathe, an ochre vertical mill and an
oxide-red power press. The sprite tree has no 2×3 prop today; check that the
editor's footprint placement and the rotated 3×2 case both behave before painting
all three. The 3D branch's sketch prompts in `FACTORY-MACHINE-PROMPTS.md` are a
usable starting point for the paintings, but the palette clause must be this
game's.

### G — Connecting conveyors · group `conveyor`

One kind with sixteen appearances: four ends, two straights, four corners, four
T-junctions and a crossing, chosen by which of the four cardinal neighbours also
holds a conveyor. Diagonals do not connect.

This is not a normal prop. The sprite game already has exactly this pattern in
`shore-tiles.js`, which picks one of sixteen masks from its neighbours and paints
an overlay; copy that structure into a new `conveyor-tiles.js` rather than adding
sixteen prop kinds. The parcel owns that new module. Transport, routing and
animation are out of scope on both branches.

### H — Canvas truck · group `vehicles`

One kind. The 3D model is about 4.7 × 1.9 units, so roughly 5×2 tiles with the cab
forward. Static scenery: no movement, no doors, no cargo. Check the rotated 2×5
case. This is the smallest Stage 1 parcel and a reasonable first parcel for an
agent new to the tree.

## Stage 2 — systems

### I — Artificial light and detection

**Depends on** S2 for the clock and the light-pool hook, and on B for fixtures to
light. Can be built against B's prop kinds before B's paintings exist.

Port `light-sources.js` from the 3D branch: the per-fixture emitter offsets, the
`LIGHT_RANGE` of 30 tiles, and the stepped falloff of 100% / 50% / 25% / 12.5% /
6.25% / 3.125% in five-tile bands. Add `lightMode` to the placed prop, authored in
the editor as Automatic, Always on, or Off, with automatic electric lamps running
18:00–06:00 and automatic fires always lit. The sprite map parser already lets an
unknown field ride on a prop record, so this needs no schema change, but it must
survive export, import, undo and block capture.

Two halves, and the second is the one that matters. The rendered half draws a
light pool through S2's hook. The tactical half adds the illumination term to
detection: sum the contributions, cap at daylight, and trace exposure from the
target's body to the source through the solids sight already uses, excluding the
source's own footprint. Light must never bypass the sight cone or line of sight.

**Owns.** `dist/tactics/light-sources.js` (new), `dist/tactics/light-render.js`
(new), `dist/tactics/visibility.js`, `dist/tactics/perception.js`,
`dist/tactics/engine.js`, `docs/tactics/ARTIFICIAL-LIGHTING.md` (new), its tests.

### J — Sweeping spotlights

**Depends on** I, whose `light-sources.js` it extends, and on C for the towers.
It cannot run at the same time as I.

`lightTargets` on the placed prop: one to three map offsets, picked in the editor,
relative so that block capture and undo preserve them. One point is stationary;
two or three interpolate in a repeating loop at one game minute per leg. A 60°
cone for the standalone `spotlight`, 45° for the three towers, gating both the
drawn beam and detection, with the same bands and occlusion as an ordinary lamp.

Then the exposure rule, which is a real change to how the game plays: any nonzero
direct spotlight illumination of a visible head, torso or leg identifies that
person at once, in any band, and sneaking, stance, foliage and distance penalties
cannot prevent it. The observer must still face the target and solid geometry
still blocks. Write it into `STEALTH.md`, because it overrides what that document
currently promises.

**Owns.** `dist/tactics/spotlight.js` (new), the spotlight sections of
`light-sources.js` and `ARTIFICIAL-LIGHTING.md`, `docs/tactics/STEALTH.md`, the
editor's aim-point picking, its tests.

### K — Ground cover: tufts and undergrowth

**Depends on** S2 for the ground-dressing hook. Independent of everything else.

Two related pieces of dressing the 3D branch added and the sprite game lacks.

Grass tufts, deterministic by tile and floor from a hashed seed, on exactly three
terrains: `ground-grass` and `woodland` get two tufts a tile, `yard` gets one tuft
on a third of its tiles, and every other terrain gets none. A tile covered by a
prop footprint is skipped. Nothing about that rule needs porting as-is, but the
determinism does: the same tile must draw the same tufts after a reload, a camera
move and a level switch.

Foliage undergrowth: where terrain is `woodland`, a darker grass and three dense
waist-height shapes per tile, instead of today's single tinted diamond and one
bush sprite.

The mechanics do not change. Woodland already costs nine tiles of optical distance
per tile crossed and already multiplies acquisition by `exp(-depth × 0.35)`;
`woodland.js` already measures the exact ray length. This parcel is the look, and
it must not add collision or cover. Determinism is the thing to test: the same
tile must draw the same tuft on every reload and after a camera move.

**Owns.** `dist/tactics/ground-cover.js` (new), `dist/tactics/woodland.js`,
`dist/assets/environment/undergrowth/*`, `art/undergrowth-prompts.md`,
`docs/tactics/GROUND-COVER.md` (new), its tests.

## Stage 3

### M — Repainting the existing catalog

Runs alone, because it rewrites PNGs every other parcel reads. Take it last, or
take it first and land it before Stage 1 starts; do not interleave it.

The 3D branch improved art for scenery this game already has. Each item below is a
repaint of an existing id at the existing crop conventions, not a new kind:

- `fence-chainlink` and `fence-cut`: clipped diagonal wire rather than a flat mesh.
- `wall-brick`: twelve varied courses instead of eight uniform ones, brick lengths
  around .325–.385 world units, recessed mortar, a dressed-stone doorway and
  coping, strong brush marks reserved for a minority of bricks.
- `crate-wood`: individual planks, grain aligned to the boards and braces, nail
  heads, selective rubbed edges, without dense high-contrast grain.
- `barrel-single` and `barrels-cluster`: rounded shoulders, a mild belly and dent,
  rolled rings, lid and bung.
- `roof-corrugated-sloped`: a continuous wedge underside rather than stepped boxes.
- `medicine-cabinet` and `medicine-cabinet-open`: front-opening doors, smoother
  equipment metal.

The independent reviewer on the 3D branch reached this look over three passes and
rejected the first two for reading coppery, over-polished and too busy. Read
`PAINTED-ENVIRONMENT-STUDY.md` before starting so the same ground is not lost
twice. Each repaint must keep its id, its footprint, its crop conventions and its
silhouette; a changed silhouette changes what the player reads as cover.

**Owns.** The named PNGs under `dist/assets/environment/` and
`dist/assets/environment/facility/`, their `prop-art.js` crops, and
`art/environment-prompts.md`.

**Does not cover character art.** The existing-art lock is over the environment
catalog only. Nothing under `dist/assets/characters/` belongs to this parcel or to
any other parcel in this plan. See the scope note below.

## Working rules

- Branch from `tactics-prototype`, one branch per parcel, named for the parcel.
  Work in your own `git worktree`; three agents share this clone, so run
  `git status` first and never check out over somebody else's work.
- Claim a parcel by filling in its row in the status table above and pushing that
  one commit before you start. Release it the same way if you stop.
- Stage the files you touched by name. Never `git add -A` in this tree.
- `npm run check` must pass before handover. It is `node --check` over nineteen
  modules, `node --test tests/*.test.mjs`, and the asset validator, and the asset
  validator is the one that will catch a half-registered prop.
- Take one independent hostile review per parcel and reach at least 9/10 before
  handing over, matching the gate the 3D branch's own sections use. Review the
  art from screenshots at gameplay size beside a standing character, not only from
  a test count. A passing suite cannot raise an art score.
- Record in your parcel's section: the commit, the review page, the checks run,
  the review score, and what you did not cover.

## Open questions for the architect

1. **Do the four art libraries become prop kinds at all?** Towers beyond the three
   canonical ones, furniture, cargo forms, machines, the conveyor and the truck are
   explicitly not map prop kinds on the 3D branch. Porting them to sprites creates
   fifteen or more new canonical kinds. Parcels D through H are blocked on a yes.
2. **Mature trees: repaint or upscale?** Upstream aliases the existing 2D artwork
   at 1.8×. This plan recommends two new paintings.
3. **Does the sprite game want a day cycle at all?** S2 is the foundation of
   everything in Stage 2, and it changes how every existing map looks at 21:00.
   The campaign clock already runs; nothing currently reads the hour.
4. **The spotlight instant-reveal rule** overrides sneaking, stance and foliage
   concealment. That is a balance decision, not a visual one, and `STEALTH.md`
   currently promises the opposite.
5. **Wall-mounted props** have no precedent here. `wall-torch` and
   `gooseneck-sconce` need an edge-mounting convention before B can finish.
6. **Three-story props** need a sorting and dimming rule before C can finish.
